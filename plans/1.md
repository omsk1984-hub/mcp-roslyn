# Анализ диалога: случаи, где Roslyn помог бы с первого раза

Изучил лог работы агента над планом 27 (добавление инструментов `validate_edit`, `format_document`, `apply_fix`, `extract_method` в MCP-сервер `roslyn-codelens`). Нашёл **8 характерных эпизодов**, где агент спотыкался, гадая по памяти о внутренностях Roslyn или API, вместо того чтобы сразу спросить у самого Roslyn через MCP.

---

## Кейс 1. Гадание о `CodeAction.NestedActions` у Extract Method

**Что произошло (несколько итераций):**
> «Стоп. Может быть проще: Roslyn extract method поддерживает "prompt user for method name" через nested actions? В VS есть "Extract Method…" с диалогом — это `ExtractMethodCodeRefactoringProvider` создаёт action с `NestedActions`? Мы эмпирически увидели: get_code_actions вернул 2 действия без вложенных... `nestedActions` = null. Значит нет.»
>
> «Хм, на самом деле в Roslyn есть `ExtractMethodCodeRefactoringProvider` и `ExtractMethodGenerator`... Но наш get_code_actions не показал вложенных…»
>
> «Посмотрим на `ExtractMethodCodeAction`: в Roslyn... Хм, но заголовок был просто "Извлечь метод". Возможно провайдер возвращает одно действие "Extract method" (с NewMethod) плюс вложенные с именами — и наш get_code_actions их обрезал? Нет, totalCount=2.»
>
> «ОК. Эмпирика: давайте напишу quick probe — временный тестовый файл?»

**Почему неэффективно:** агент 4–5 раз пересказывал вслух гипотезы о внутреннем устройстве `Microsoft.CodeAnalysis.CSharp.Features.ExtractMethod`, не имея фактов. Каждый «Хм» — это потерянный цикл рассуждения.

**Как Roslyn помог бы сразу:** один вызов `get_code_actions` на реальном файле с выделенным диапазоном + параметр `includeNested: true` (или probe-тест) дал бы точный ответ: есть `NestedActions` или нет. Факт установился бы за 10 секунд, а не за 15 минут размышлений.

## Кейс 2. Матчинг действия по заголовку vs `EquivalenceKey`

**Что произошло:**
> «Ключевое требование — определять extract-method action по `CodeAction.Kind`/типу провайдера, а не по тексту заголовка.»
>
> «В Roslyn `ExtractMethodCodeRefactoringProvider.CreateCodeAction` использует `CodeAction.Create(Title, ct => ..., EquivalenceKey)`. Эквивалентность — не Kind. Так что Kind может быть "" .»

Позже это вылилось в целую секцию «Нюанс 10» в правилах:
> «### Нюанс 10: заголовки Roslyn-действий локализованы… - Причина: `CodeAction.Title` локализован, `CodeAction.EquivalenceKey` — нет.»

**Почему неэффективно:** агент рассуждал о `Kind` (которого у refactoring-ов почти никогда нет), прежде чем вспомнить про `EquivalenceKey`. На ru-RU сборке это привело бы к молчаливому провалу — `get_code_actions` возвращает «Извлечь метод», а код ищет «Extract method».

**Как Roslyn помог бы:** `get_code_actions` возвращает и `title`, и `equivalenceKey` одновременно. Один реальный вызов показал бы: `title = "Извлечь метод"`, `equivalenceKey = "Extract_method"`. Матчинг по второму полю стал бы очевидным сразу.

## Кейс 3. `TextLine.Length` — ошибка API, пойманная компилятором

**Что произошло:**
Агент написал в `FormatDocumentLogic.cs`:
```csharp
var endOffset = endLineObj.Position + endLineObj.Length;
```
Компилятор ответил:
> `error CS1061: "TextLine" не содержит определения "Length"`

Позже в diff видно исправление:
```diff
- var endOffset = endLineObj.Position + endLineObj.Length;
+ var endOffset = originalText.Lines[endLine - 1].End;
```

**Почему неэффективно:** агент писал код «по памяти» об API `Microsoft.CodeAnalysis.Text.TextLine`, не проверив доступные свойства. Компилятор поймал, но это стоило цикла build→error→fix.

**Как Roslyn помог бы:** `get_symbol_context` или `get_type_overview` для `TextLine` мгновенно показал бы свойства `Start`, `End`, `Span`, `SpanIncludingLineBreak` — и `Length` не появился бы в коде.

## Кейс 4. `SyntaxNode` vs `SyntaxTree` — путаница типов

**Что произошло:**
В `ExtractMethodLogic.cs` на строках 144, 209, 240:
> `CS1503: Аргумент 1: не удается преобразовать из "Microsoft.CodeAnalysis.SyntaxNode" в "Microsoft.CodeAnalysis.SyntaxTree"`

**Почему неэффективно:** классическая ошибка при работе с Roslyn — перепутать корень дерева (`SyntaxNode`, результат `GetSyntaxRootAsync`) и само дерево (`SyntaxTree`). Агент писал код, не сверяясь с сигнатурами методов.

**Как Roslyn помог бы:** `get_method_source` для `Document.WithSyntaxRoot()` / `compilation.ReplaceSyntaxTree()` показал бы точные сигнатуры. Либо `get_diagnostics` в режиме live-проверки во время написания кода.

## Кейс 5. Тесты `ValidateEditLogic` падают из-за отсутствия `System.Object`

**Что произошло:**
> `CS0518: Предопределенный тип "System.Object" не определен или не импортирован`
> `CS1729: "object" не содержит конструктор, который принимает аргументы 0.`

Тесты `CleanFile_Passes`, `BaselineDelta_NewErrorReported`, `SyntaxError_Fails_WithCsError` падали.

**Почему неэффективно:** агент собирал `CSharpCompilation` в тестах без `MetadataReference` на `System.Runtime` / `typeof(object).Assembly`. Это базовая грабля Roslyn-тестов, но она повторялась.

**Как Roslyn помог бы:** в логе видно, что в `ExceptionAnalyzerTests.cs` уже есть правильный паттерн:
```csharp
MetadataReference.CreateFromFile(typeof(object).Assembly.Location)
```
Вызов `find_references` на `MetadataReference.CreateFromFile` по кодовой базе показал бы все существующие примеры сборки тестовых компиляций — и агент с первого раза скопировал бы рабочий шаблон.

## Кейс 6. `ApplyFixLogicTests.Cs0246_Apply_FixesError` — фикс не добавил `using`

**Что произошло (несколько запусков):**
> `Assert.Contains() Failure: Sub-string not found`
> `String: "namespace FixDemo;\public class Foo{"···`
> `Not found: "using System.Collections.Generic;"`

Агент запускал `dotnet test --filter Cs0246_Apply_FixesError` минимум 4 раза, пытаясь понять, почему `apply_fix` не добавляет `using`.

**Почему неэффективно:** вместо того чтобы посмотреть, какие именно `CodeAction` возвращает `get_code_fixes` для `CS0246` (там может быть несколько: "using System.Collections.Generic", "Generate class", "Generate method"…), агент дебажил вслепую.

**Как Roslyn помог бы:** один вызов `get_code_fixes` на реальном `CS0246` с позицией показал бы список фиксов с их `EquivalenceKey`. Агент сразу увидел бы, что нужный фикс существует, и проверил бы, почему `ApplyFixLogic` его не находит (спойлер: снова локализация заголовков или несовпадение `EquivalenceKey`).

## Кейс 7. `ExtractMethodLogicTests` — метод не стал `private` и тело не вычистилось

**Что произошло:**
> `Not found: "private void EmitPrefix()"`
>
> `Assert.DoesNotContain() Failure: Sub-string found`
> `Found: "Console.WriteLine(a);"` (т.е. тело осталось в исходном методе)

**Почему неэффективно:** агент предположил, что Roslyn extract-method:
1. автоматически делает метод `private` (а он делает его с модификатором по умолчанию),
2. удаляет исходный код из тела (а он оставляет вызов нового метода, но в тесте ожидалось именно удаление).

Это знания о поведении Roslyn-провайдера, которые нельзя вывести рассуждением — их можно только наблюдать.

**Как Roslyn помог бы:** запуск `apply_code_action` в режиме `preview: true` на фикстуре показал бы точный результат правки до того, как агент начал бы писать тесты на ожидаемое поведение. Тесты писались бы по факту, а не по догадке.

## Кейс 8. Текстовые `searchFiles` вместо семантического поиска

**Что произошло (множество раз в логе):**
```
searchFiles regex: "PreviewOrApplyAsync"
searchFiles regex: "delegate.*CommitWrittenDocuments|CommitWrittenDocuments"
searchFiles regex: "ApplyFixTool|GetCodeActionsTool|ValidateEditTool"
searchFiles regex: "enum ToolErrorCode|record TextEdit|record RenameConflict"
```

**Почему неэффективно:** `searchFiles` с regex находит совпадения в комментариях, строковых литералах, `using static`, не различает `read` и `write`, не видит переопределений. В правилах `.roo/rules/02-roslyn-codelens.md` прямо написано:
> «Отдельно: поиск присваиваний (`X = ...`) текстовым regex — систематическая ошибка… Правильный вызов — `find_references` с фильтром `kinds: ["write", "readwrite"]`.»

Но агент продолжал использовать regex даже для поиска определений типов и делегатов.

**Как Roslyn помог бы:**
- `find_references` на `PreviewOrApplyAsync` → все вызовы с контекстом, без шума.
- `get_symbol_context` на `CommitWrittenDocuments` → определение + все использования.
- `find_implementations` / `get_type_hierarchy` для `ToolErrorCode` → полная картина.
- `search_symbols` для нечёткого поиска по имени типа.

## Общие выводы

1. **Агент знает, что у него есть Roslyn-MCP, но по инерции рассуждает о внутренностях Roslyn вслух.** Правило «сначала спроси у Roslyn, потом рассуждай» в `.roo/rules/02-roslyn-codelens.md` есть, но соблюдается не всегда.

2. **Ключевой паттерн провала:** когда агент не уверен в API Roslyn (`TextLine`, `SyntaxNode`/`SyntaxTree`, `CodeAction.NestedActions`), он пишет код «по памяти» и ждёт, пока компилятор или тесты его поправят. Это работает, но дорого.

3. **Тесты пишутся по догадке о поведении Roslyn, а не по факту.** Extract-method, `apply_fix` — в обоих случаях агент ожидал одного поведения, а Roslyn сделал другое. `preview: true` на фикстуре перед написанием теста сэкономил бы 2–3 итерации.

4. **Текстовый поиск как fallback вместо первого выбора.** Правило явно говорит использовать `find_references`, но агент всё ещё стартует с `searchFiles` для поиска символов.

**Рекомендация для правил:** добавить в `.roo/rules-code/03-roslyn.md` явный запрет: *«Прежде чем рассуждать о внутренностях Roslyn-типов (`CodeAction`, `TextLine`, `SyntaxNode` и т. п.) — вызови `get_type_overview` или `get_symbol_context`. Прежде чем писать тест на поведение Roslyn-провайдера — запусти `apply_code_action` в `preview: true` на фикстуре».*
