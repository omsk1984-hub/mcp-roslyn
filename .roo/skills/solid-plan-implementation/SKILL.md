# Скилл: ручное выполнение SOLID-плана с MCP-проверками и TDD

Цель — реализовать поэтапный план из `plans/*solid*plan*.md` (созданный
скиллом `solid-architecture-audit`) без регрессий. Ключевой принцип:
**каждый пункт плана — отдельный цикл «красный тест → правка → зелёный
тест → MCP-проверка → коммит»**.

Режим выполнения: **Code**.

> Базовые правила работы с MCP (жизненный цикл решения, дефекты инструментов,
> безопасность) — в скилле `roslyn-codelens-usage`. Здесь только цикл реализации.

---

## 0. Опорные факты о MCP-сервере (проверено эмпирически 2026-10-25)

MCP-сервер `roslyn-codelens` — инструмент **верификации и точечного
рефакторинга**. Массовые структурные преобразования (извлечение интерфейсов,
перенос логики) по-прежнему выполняются вручную.

### 0.1. Что работает надёжно (анализ, только чтение)

| Инструмент | Назначение в цикле |
|---|---|
| `find_references` | До правки: полный список мест, которые затронет изменение сигнатуры (с видами ссылок) |
| `analyze_change_impact` | Blast radius: файлы, проекты, вызывающие — одной командой |
| `find_callers` / `get_call_graph` | Подтвердить, что путь исполняется, а не мёртвый код |
| `get_method_source` / `get_symbol_context` | Точная сигнатура/члены/исходник до и после правки |
| `get_file_overview` | Каркас файла для точных `apply_diff` |
| `get_diagnostics` | **После каждой правки**: 0 ошибок (severity = error, затем warning) |
| `get_complexity_metrics` | **После этапа**: подтвердить снижение сложности |
| `get_type_hierarchy`, `find_implementations` | Контроль полноты при изменении контрактов |
| `search_symbols` | Поиск дубликатов имён методов/констант по решению |
| `find_unused_symbols` | Контроль, что правка не оставила мёртвый код |

### 0.2. Что работает как рефакторинг (подтверждено preview)

| Инструмент | Статус |
|---|---|
| `rename_symbol` | Работает с `preview: true` (по умолчанию): каскад на ссылки, конструкторы, nameof, XML-doc; `conflicts` в ответе. Проверено на `ToolRegistry.Find` → `TryFind`: 4 файла, включая интерфейс и тесты |
| `change_signature` | Работает с `preview: true`: добавление/удаление/перестановка параметров с обновлением всех вызовов; каскад на переопределения и реализации интерфейса (`cascadedTo`) |
| `apply_code_action` | Работает с `preview: true`: применяет рефакторинги из `get_code_actions` (например «использовать тело выражения») |
| `get_code_fixes` | Возвращает структурированные правки для конкретного диагностического ID |

**Все изменяющие инструменты по умолчанию в режиме предпросмотра** —
файлы не пишутся, пока явно не передано `preview: false`.

### 0.3. Известные дефекты и ограничения (обходные пути)

| Дефект | Обход |
|---|---|
| `get_exception_flow` не находит конструкторы (`SymbolNotFound`) | Для исключений из конструкторов — `find_throw_sites` |
| `find_tests_for_symbol` находит не все прямые тесты (вызовы через локальные переменные, `Assert.Throws`) | Источник истины по покрытию — `get_test_summary` (referencedSymbols) и `find_uncovered_symbols` |
| `analyze_data_flow` / `analyze_control_flow` падают, если диапазон пересекает границы блоков | Диапазон строк — внутри одного списка операторов (одной пары `{ }`) |
| `resolve_stack_trace` не резолвит кадры `File.cs:30` | Формат кадров `... in File.cs:line 30` (Exception.ToString()) |

### 0.4. Чего MCP не умеет в принципе (всегда вручную)

- извлекать интерфейс/метод/базовый класс (старые инструменты
  `extract_interface`, `extract_method`, `encapsulate_field`,
  `convert_to_async` в этом сервере **отсутствуют**);
- менять тип члена record (`IReadOnlyList<object>` → `IReadOnlyList<Finding>`);
- писать логику маппинга/парсинга (новый код);
- добавлять новые методы и вызовы к ним (например `Reset()` в реестр);
- переносить куски логики между классами;
- менять несколько скоординированных файлов одновременно (контракт →
  реализация → вызывающий) — но `rename_symbol`/`change_signature`
  обновляют вызовы автоматически;
- писать тесты (`generate_test_skeleton` даёт только каркас; путь и
  пространство имён каркаса сверять с фактической структурой тестов).

## 1. Подготовка

1. Прочитать план (`plans/…`), выписать пункты текущего этапа в todo
   (`update_todo_list`) — по одному пункту на элемент.
2. Убедиться, что рабочее дерево чистое:
   `git status --porcelain` → пусто. Если не чисто — спросить пользователя,
   как поступить (не коммитить чужие изменения).
3. Базовый прогон тестов ДО любых правок:
   `dotnet test src/LLMNetHelper/LLMNetHelper.slnx`
   Зафиксировать стартовое число пройденных/упавших/пропущенных.
4. Базовая диагностика: `get_diagnostics` (severity = warning) —
   зафиксировать стартовый набор.
5. Проверить состояние сервера: `list_solutions` — решение активно;
   после массовых правок между этапами — `rebuild_solution` при подозрении
   на устаревшие диагностики.

## 2. Цикл выполнения одного пункта

Повторять для каждого пункта этапа строго последовательно:

### 2.1. Red — тест, фиксирующий дефект

- Найти существующий тестовый файл по области
  (`LLMNetHelper.Tests/<Область>/*Tests.cs`); если нет — создать новый
  (каркас: `generate_test_skeleton`, доработать вручную).
- Написать тест, который **падает на текущем коде** и описывает желаемое
  поведение. Обязательно с комментарием, какой дефект плана он фиксирует
  (например `// Дефект D1: находки теряются при маппинге Diagnosis → AnalysisResult`).
- Запустить точечно:
  `dotnet test src/LLMNetHelper/LLMNetHelper.Tests/LLMNetHelper.Tests.csproj --filter <ИмяТеста>`
  Ожидание: **FAILED**. Если тест прошёл — дефект не воспроизводится;
  разобраться (возможно, путь не исполняется — проверить `find_callers`)
  прежде чем править код.

### 2.2. Green — минимальная правка

- До правки: `analyze_change_impact` (или `find_references`) по каждому
  изменяемому символу — полный список мест. Править **все** места в одном
  `apply_diff`/наборе правок, иначе решение не скомпилируется.
- Переименования и изменения сигнатур выполнять инструментами сервера,
  а не вручную: `rename_symbol` / `change_signature` с `preview: true`,
  проверить `edits` и `conflicts`, затем `preview: false`. Это гарантирует
  каскад на все вызовы, переопределения и реализации интерфейса.
- Вносить только изменения, необходимые для прохождения теста. Никакой
  попутной реструктуризации (это следующий этап плана).
- После правки:
  1. `get_diagnostics` по затронутому проекту → 0 ошибок;
  2. точечный тест того же фильтра → **PASSED**;
  3. полный прогон `dotnet test src/LLMNetHelper/LLMNetHelper.slnx` →
     не меньше пройденных, чем на шаге 1.3, и 0 падений.

### 2.3. Verify — MCP-контроль

- `find_references` по исправленному символу — убедиться, что нигде не
  осталось старой сигнатуры/мёртвых вызовов.
- Если пункт менял контракт: `find_implementations` — все реализации
  синхронизированы.
- Если пункт удалял/переносил тип: `get_type_hierarchy` — нет «осиротших»
  наследников; `find_unused_symbols` — не появился мёртвый код.
- Если пункт менял обработку ошибок: `get_exception_flow` по методу
  (для конструкторов — `find_throw_sites`) и `find_catch_blocks` —
  исключения перехватываются там, где задумано.

### 2.4. Commit

- Один пункт = один коммит. Сообщение:
  `fix(stage0.<N>): <суть> (план 18, дефект D<M>)`.
- Не объединять пункты в один коммит — это ломает возможность точечного
  отката.

### 2.5. Если пункт не проходит

- Откатывать только этот пункт (`git checkout -- <файлы>`), фиксировать
  причину в плане (`plans/18_solid-improvement-plan.md`, снять галочку,
  добавить примечание), переходить к следующему. Не оставлять полуизменения.

## 3. Завершение этапа

1. Полный прогон: `dotnet test src/LLMNetHelper/LLMNetHelper.slnx` — все
   зелёные (сетевые помечены `Category=Integration` и остаются Skipped).
2. `get_diagnostics` (warning) — 0.
3. `get_complexity_metrics` по затронутым файлам — зафиксировать динамику
   (цикломатическая/когнитивная сложность) в плане; при декомпозиции —
   `find_large_classes` / `find_god_objects` до/после.
4. Отметить пункты этапа как выполненные в `plans/…md` (галочки `[x]`)
   и добавить строку «Статус: этап N завершён <дата>».
5. Переходить к следующему этапу только после закрытия критериев готовности
   текущего (раздел 5 плана).

## 4. Специфика этапов плана (подсказки)

| Этап | Основной механизм | MCP-опора |
|---|---|---|
| 0 — дефекты | Ручные `apply_diff` + TDD | `analyze_change_impact`, `find_references`, `get_diagnostics`, `find_async_violations` (sync-over-async) |
| 1 — типобезопасность | Вручную: enum + конвертеры на границах сериализации | `search_symbols` по строковым литералам, `find_references` |
| 2 — интерфейсы/DIP | Вручную: писать интерфейс, менять параметр, DI-регистрацию (инструмента извлечения интерфейса нет) | `get_symbol_context` (члены), `find_implementations` (полнота), `get_di_registrations` |
| 3 — ReAct-цикл | Сначала паритетные тесты, потом перенос кода вручную | `find_callers`, `get_call_graph`, `analyze_data_flow` для региона цикла (один блок) |
| 4 — декомпозиция | Вручную: выделять классы/обработчики; переименования — `rename_symbol` | `get_complexity_metrics` до/после, `find_god_objects` |
| 5 — пайплайн | Вручную: `int Order` + сортировка в `AgentPipeline` | `find_references` по `IRunStep`, `check_architecture` |
| 6 — тестируемость | Вручную: интерфейс + DI-регистрация вместо static | `get_symbol_context`, `find_uncovered_symbols` после этапа |
| 7 — транспорт | Вручную, под флагом конфигурации | паритетные тесты SK/native, `get_test_summary` |

## 5. Запреты

- Не менять поведение без падающего теста заранее.
- Не применять `rename_symbol` / `change_signature` / `apply_code_action`
  с `preview: false` на грязном дереве и без проверки `conflicts`.
- Не запускать скрипты как `.\script.ps1` (уйдёт в Блокнот) — только явный
  вызов `pwsh` с UTF-8-префиксом (правило проекта 02-powershell.md).
- Не останавливать никакие процессы без явного разрешения пользователя.
- Не объединять несколько пунктов плана в один коммит.
- Не править исторические/архивные документы в `plans/` как конфигурацию.
