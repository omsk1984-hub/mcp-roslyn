# Скилл: SOLID-аудит решения C# через roslyn-codelens MCP

Цель скилла — воспроизводимая методология аудита архитектуры и кодовой базы
решения C# (`.slnx`/`.csproj`) с обязательным использованием инструментов
MCP-сервера `roslyn-codelens` и оформлением результата как поэтапного плана
улучшений в `plans/`.

Рекомендуемый режим выполнения: **Architect** (только чтение + план в `.md`).

> Базовые правила работы с MCP (жизненный цикл решения, дефекты инструментов,
> безопасность) — в скилле `roslyn-codelens-usage`. Здесь только сценарии аудита.

## Фаза A. Подготовка и проверка окружения

1. `list_solutions` — убедиться, что решение загружено и активно
   (`isActive: true`, `status: "ready"`). Если нет — `load_solution` с
   абсолютным путём к `.slnx`.
2. Проверить чистоту компиляции: `get_diagnostics` с `severity: "error"`,
   затем `severity: "warning"`. Для диагностик анализаторов —
   `includeAnalyzers: true` (требует доверия: проверить `list_trusted_paths`,
   при необходимости `trust_solution` со `scope: "session"`).
3. Быстрый срез здоровья: `get_project_health` с `hotspotsPerDimension: 5` —
   единый ответ по 7 измерениям: сложность, крупные классы, именование,
   мёртвый код, рефлексия, async-нарушения, disposable.

## Фаза B. Инвентаризация абстракций и контрактов

Каркас для оценки ISP/DIP/LSP:

1. `get_public_api_surface` — полный список публичных типов и членов
   (в этом решении ~942 записи) с разбивкой по проектам.
2. По каждому интерфейсу из Abstractions: `get_type_overview` (контекст +
   иерархия + диагностики одним вызовом) и `get_symbol_context`
   (кто внедряет интерфейс через конструктор).
3. `get_di_registrations` по ключевым абстракциям (`IAgentTool`,
   `IFactStore`, `IReportWriter`…) — карта DI и место поиска Service Locator.
4. Композиционный корень: `read_file` `Program.cs`, `DependencyInjection*.cs`,
   `*Registration*.cs`.

Ключевые вопросы на этом этапе:

- Есть ли в контрактах `IReadOnlyList<object>`, `object`, `string` там,
  где должен быть типизированный доменный тип или `enum`?
- Есть ли `IDisposable`/методы инициализации в интерфейсах, навязывающие
  реализацию всем наследникам (LSP)?
- Сколько методов в интерфейсе и смешивают ли они разные сущности (ISP)?
  (`get_symbol_context` показывает список публичных членов.)
- Смешаны ли в интерфейсе запросы и команды (CQS)?

## Фаза C. Трассировка потоков данных (поиск дефектов)

Для каждой предметной области, названной пользователем (оркестрация,
промпты, Git, правки кода, отчёты, разбор ответов LLM и т.п.):

1. `find_references` по ключевым типам (модели результатов, интерфейсы) —
   полный граф использования с видами ссылок (read/write/cast/invocation).
2. `get_method_source` (батчевый) — исходники производителей и потребителей.
3. Проверить типовые дефекты маппинга/сериализации:
   - **потеря типа**: коллекция объявлена как `IReadOnlyList<object>`,
     производитель кладёт `JsonElement`, а потребитель фильтрует `item is T`
     → данные молча теряются;
   - **двойная сериализация**: рендерер возвращает готовую JSON-строку,
     а писатель принимает `object` и сериализует повторно;
   - **несогласованные контракты**: один вход обрабатывается двумя парсерами
     с разной валидацией — проверить `get_call_graph` обоих путей;
   - **sync-over-async**: `find_async_violations` находит `.Result`/`.Wait()`
     автоматически (паттерн SyncOverAsync);
   - **semantics misuse**: метод с узкой семантикой используется для записи
     артефактов другого рода — `find_callers` + чтение тел.
4. `analyze_change_impact` для подозрительных методов — подтвердить, что
   дефектный путь реально исполняется (есть вызывающие), а не мёртвый код.
5. Исключения на путях: `get_exception_flow` по подозрительному методу —
   какие исключения покидают его и где перехватываются;
   `find_catch_blocks` с `includeBaseClauses: true` — кто глотает
   (`swallowing` в сводке). Для конструкторов — только `find_throw_sites`
   (дефект `get_exception_flow`, см. скилл `roslyn-codelens-usage` §4).

## Фаза D. Метрики кода (SRP, god-классы, крупные классы)

Инструменты сервера `roslyn-codelens` дают метрики напрямую:

1. `get_complexity_metrics` (metric = cyclomatic, threshold = 10) —
   худшие методы по цикломатической сложности; поле `cognitive` —
   когнитивная сложность, `maxNesting` — глубина вложенности.
2. `find_large_classes` (maxLines = 300, maxMembers = 15) — кандидаты
   в god-классы по размеру.
3. `find_god_objects` — размер × зацепление: `minLines`, `minMembers`,
   `minFields`, `minIncomingNamespaces`, `minOutgoingNamespaces`.
   Инструмент сам отсекает DTO (только поля) и диспетчеры (только члены):
   тип попадает в список только при превышении **всех трёх** порогов размера
   и хотя бы одного порога зацепления.
4. Пороги внимания:
   - цикломатическая сложность > 15 — кандидат на декомпозицию;
   - когнитивная сложность > 25 — метод тяжело читать;
   - строк > 300 и членов > 15 — кандидат в god-классы;
   - входящих/исходящих пространств имён ≥ 5 — сильное зацепление.
5. Для каждого проблемного класса `get_symbol_context` или
   `get_type_overview` — список членов и оценка смешанных ответственностей.
6. Итог фазы — таблица «класс / CC / cognitive / LOC / члены / зацепление».

## Фаза D2. Нарушения инкапсуляции и мёртвый код

1. **Публичные поля**: `find_naming_violations` ловит приватные поля без `_`,
   но публичные поля ищите через `get_public_api_surface` с фильтром
   записей `kind: Field`.
2. **Изменяемое публичное состояние доменных типов**: `get_symbol_context`
   по модели — свойства с сеттерами в контекстах/моделях признак mutable
   shared state (пример: `RunContext` с 14 публичными изменяемыми свойствами).
3. **Состояние, протекающее между прогонами**: у зарегистрированных
   singleton-сервисов (`get_di_registrations` → lifetime Singleton) проверить
   приватные изменяемые поля через `get_method_source`/`read_file`.
4. **Мёртвый код**: `find_unused_symbols` (includeInternal для полноты).
   Каждый кандидат перепроверить `find_references` (рефлексия, сериализация,
   DI не видны как ссылки) перед пометкой на удаление.
5. **Проверка иерархий**: `get_type_hierarchy` — базовые типы, наследники,
   интерфейсы; глубокие или пустые иерархии — материал для фазы E (LSP).
6. **Устаревший API**: `find_obsolete_usage` — использования `[Obsolete]`.

## Фаза E. Проверка нарушений SOLID и антипаттернов

Систематический обход по чек-листу (использовать `search_symbols` /
`codebase_search` / `read_file` + инструменты ниже):

### SRP
- Классы из фазы D: перечислить ответственности каждого
  (`get_symbol_context` — список членов).
- Шаги пайплайнов: не делает ли шаг чужую работу?

### OCP
- Проверки конкретного типа: `search_files` по `is\s+ConcreteClass` там,
  где объявлен интерфейс.
- Зашитый порядок: порядок шагов/обработчиков определяется порядком
  DI-регистраций, а не декларативно? (`get_di_registrations`)
- Парсинг форматов, зашитый в исполняющий класс?

### LSP
- `IDisposable`, обязательная инициализация и другие требования контракта,
  которые не каждая реализация может честно выполнить
  (`find_implementations` по интерфейсу — все ли реализации честны).
- Временнóе зацепление: вызов обязан происходить в определённом порядке,
  не выраженном типами (`get_call_graph` callers).

### ISP
- Жирные интерфейсы (>7 методов разных сущностей) — `get_symbol_context`.
- Смешение запросов и команд в одном интерфейсе.
- `object`/строки вместо доменных типов в сигнатурах — `get_overloads`.

### DIP
- Конструкторы принимают конкретные классы вместо интерфейсов:
  `get_instantiation_options` показывает параметры конструкторов и
  `requiredMembers`; `get_symbol_context` — `injectedDependencies`.
- `new ConcreteClass(...)` внутри прикладных классов: `search_files` по
  `new\s+Concrete` вне композиционного корня.
- Разрешение конкретных типов через контейнер: `search_files` по
  `GetRequiredService<` вне композиционного корня = **Service Locator**.

### Антипаттерны
- **Дублирование логики**: `search_symbols` по имени метода — несколько
  определений в разных классах.
- **Singleton с состоянием**: `get_di_registrations` (lifetime Singleton) +
  изменяемые поля (`find_references` kinds = write).
- **Магические строки**: вердикты/статусы строками без `enum`.
- **Статические классы-сервисы**: `search_symbols` — не подменяются в тестах.
- **Mutable shared context**: изменяемый объект-контекст между шагами.
- **Утечки ресурсов**: `find_disposable_misuse` (DisposableNotDisposed /
  DisposableDiscarded) и `find_event_subscribers` (подписки без отписки).

## Фаза F. Архитектурные границы и тестируемость

1. **Циклы зависимостей**: `find_circular_dependencies` (level = project,
   затем namespace).
2. **Слоистость**: `check_architecture` с правилами проекта, например:
   - `forbid`: Abstractions → Core/Agent/Infrastructure;
   - `allowOnly`: Roslyn → Abstractions + Roslyn.
   Поле `to` — всегда массив строк. Помнить: `allowOnly` не видит ссылки на
   framework/metadata (для их запрета — явный `forbid`).
3. **Покрытие тестами**:
   - `get_test_summary` — инвентаризация тестов (фреймворк, атрибуты,
     на какие продакшн-символы ссылается каждый тест);
   - `find_uncovered_symbols` — публичные члены без тестов, сортировка по
     сложности, `riskHotspotCount` — непокрытые со сложностью ≥ 5;
   - `find_tests_for_symbol` — только эвристика (ненадёжен для вызовов через
     локальные переменные; см. скилл `roslyn-codelens-usage` §4 дефект 2).
4. Классы без интерфейсов и со статическими зависимостями = нетестируемы.
5. Проверить паритетные/контрактные тесты у параллельных реализаций одного
   контракта (например два оркестратора).

## Фаза G. Оформление результата

Создать/обновить план в `plans/` (markdown). Обязательная структура:

1. **Результаты аудита**
   - что уже хорошо (существующие паттерны) — таблица;
   - подтверждённые дефекты — таблица: дефект, механизм, ссылки на файлы
     с номерами строк;
   - нарушения SOLID — по одному разделу на букву, таблицы со ссылками;
   - антипаттерны — таблица;
   - метрики проблемных классов (CC/cognitive/LOC/зацепление) — таблица.
2. **Целевая архитектура** — mermaid-диаграмма (без кавычек и скобок внутри
   квадратных блоков).
3. **Поэтапный план**. Порядок этапов обязателен:
   - Этап 0 — неотложные дефекты (без изменения структуры);
   - Этап 1 — типобезопасность домена (enum вместо строк, типизированные
     коллекции);
   - Этап 2 — интерфейсы и DIP (извлечение интерфейсов, сегрегация жирных);
   - Этап 3 — устранение дублирования и стандартизация циклов/движков
     (с паритетными тестами ДО рефакторинга);
   - Этап 4 — декомпозиция god-классов и устранение Service Locator;
   - Этап 5 — пайплайн/контекст (явный порядок, неизменяемость);
   - Этап 6 — тестируемость и сериализация (интерфейсы вместо статических
     классов, единые опции сериализации, контрактные тесты);
   - Этап 7 — архитектурные улучшения (транспорт, нативные механизмы).

   Для каждого этапа указать: **цель**, **конкретные изменения** (таблица
   со ссылками на файлы), **затронутые области**, **критерий готовности**,
   **влияние на существующее поведение**, **риски**.
4. **Зависимости этапов** — mermaid-диаграмма.
5. **Глобальные критерии готовности** — список.
6. **Сводка рисков** — таблица: риск, этапы, мера.

Правила оформления:

- Каждая ссылка на код — кликабельная: ``[`Имя`](относительный/путь.cs:строка)``.
- Без оценок трудозатрат по времени.
- Каждый этап должен завершаться прогоном тестов решения и отдельным
  коммитом.

## Извлечённые уроки (из аудитов 2026-10)

- Дефект «потеря данных при фильтрации по типу» ищется трассировкой:
  производитель → объявленный тип коллекции (`object`) → потребитель с
  `is T`. Обязательно читать оба конца цепочки (`get_method_source` батчем).
- Двойная сериализация ищется сопоставлением возвращаемого типа рендерера
  (`string`) и типа параметра писателя (`object`).
- `find_references` по record-модели до изменения её сигнатуры даёт полный
  список мест, которые затронет правка (оценка риска этапа).
- Если два класса декларируют «семантическую эквивалентность» (комментарий
  в коде), проверять побайтовое совпадение их парсеров — частый источник
  расхождений поведения.
- `find_async_violations` и `find_disposable_misuse` находят системные
  проблемы за один вызов — запускать их в фазе A, а не вручную.
